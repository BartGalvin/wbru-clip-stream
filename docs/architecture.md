# Architecture

The **program server** owns the clip catalog and decides what plays. The **browser
pages** render the stream and provide tools for managing the catalog.

```text
Browser pages -> Express API -> SQLite catalog
                      ^
                      |
Clip files -> Indexer -> Local scan cache (clips-cache.json)
```

## Data model

`program.db` is authoritative. It lives beside `clips-cache.json` in `TAGGER_DATA_DIR`
(local default `server/`) unless `DATABASE_PATH` overrides the database path. It contains:

- discovered clips and their availability,
- tags and source labels keyed by clip id,
- the ordered tag vocabulary,
- metadata edit history,
- scheduled clip starts for server-owned outputs.

`clips-cache.json` is a generated local scan cache. The indexer reuses its file IDs and durations
between scans; the server imports its file metadata and availability into SQLite.
Tags and source labels remain in SQLite, including for files missing from a scan.
Regenerate the cache with `npm run index-clips`.

Clip ids are sampled-content fingerprints generated by `scripts/index-clips.mjs`. They
normally survive renames and moves. Folder paths remain available for navigation; tags are
assigned through the tagger or tagging API.

Database reads return playout timestamps as UTC ISO 8601 strings.

`createSchema()` defines the current tables and indexes. Update the schema and its
database tests together. `npm run backup` creates consistent SQLite snapshots under
`BACKUP_DIR`.

`metadata_changes` records tag, source, and vocabulary edits in the same transaction
as the change. Each row stores a UTC ISO timestamp, batch ID, entity (`clip` or `tag`),
field, and JSON before/after values. Batch IDs group edits across clips, including
the clip changes made when deleting a vocabulary tag. Unchanged saves produce no
history. These records cover application edits, not direct SQL, and do not identify
individual operators. History is retained in the database and its backups.

## Program sequencing

A clip program is divided into laps. Each lap contains every available clip in the
selected library that matches the effective tag filter exactly once. The cursor returned
by `/api/program/upcoming` is an absolute program position, so clients can resume without
server-held session state.

Clips tagged `inactive` and untagged visualizer clips stay in the tagger but do not play.
The builder's counts and the server use the same eligibility rule from
`shared/libraries.ts`.

`server/src/config/playoutPolicy.ts` owns the duration thresholds and library-specific
black-and-white tags. `server/src/lapOrder.ts` applies that policy to derive a deterministic
order for each pool and lap. These preferences never remove clips from a lap.

Requests may provide `include`, `exclude`, and `match` filters. A request filter
replaces the channel default; otherwise the channel default applies. The builder uses the
same filter rules from `shared/tagFilter.ts` and omits filter parameters when its
selections match the channel defaults.

## Browser surfaces

`ContentClient` fetches pages from the program API, and `clipQueue` maintains the
cursor-paged queue. `src/video/` selects and runs the configured video source;
`src/audio/` does the same for station audio. Clip and HLS video are implemented.
`youtube` remains in the shared source contract but does not yet have a player. Audio
may be Icecast, HLS, embedded in the video, or absent.

- **`/stream`** (also `/`) resolves the channel, selects its normal or live program,
  and starts the matching video and audio players. Clip playback preloads the next video.
  With no `channel` parameter, it uses `all`: eligible clips in the `visualizer` library,
  not `wbru-tv`. Server-timed channels without custom filters join the server's current clip
  and offset once at startup via `/api/program/position`, then advance locally without
  periodic seeking. The title overlay updates when a different clip starts playing
  in the browser, using the title and publication year supplied with that clip.
  The `all` channel and custom-filter streams retain browser-local progress. Browsers do
  not write playout events.
- **`/playout`** shows searchable, cursor-paged history for the scheduled outputs.
  The live view keeps 100 entries per channel and polls every five seconds. Scrolling
  loads older pages. Live updates pause during searches or while a column is scrolled
  down, then resume when all columns return to the top.
- **`/builder`** and **`/tag`** are Svelte operator tools. Each uses a module-level
  runes store, action modules that update it, and components that render it. The builder
  generates filtered stream URLs; the tagger manages clip metadata and vocabulary.

`scheduledPlayout.ts` runs one schedule for each channel with a `serverTimelineOutputId`.
It records intended clip starts using catalog durations, with a 10-second fallback when
a duration is unknown. After a restart, a schedule waits out the last clip's remaining
duration or advances if that duration has elapsed.
These records describe the server schedule, not confirmation of what OBS displayed.

## Changing channels

The station lineup lives in `server/src/config/channels.ts`. A channel pairs a normal
video/audio program with an optional live replacement. Existing source kinds require only
a channel entry. A new source kind also requires a shared contract update, a player implementation in `src/video/` or `src/audio/`, and tests at those boundaries.
Channel ids appear in URLs and playout records, so treat them as stable identifiers.

## Server layout

- `index.ts` opens the database and starts the HTTP server on the loopback interface.
- `app.ts` assembles the Express application without listening, which keeps HTTP tests
  straightforward.
- `routes/`, `program.ts`, and `lapOrder.ts` expose and sequence channel programs.
- `db.ts` and `db/` own storage, manifest reconciliation, metadata, and playout records.
- `rescan.ts` coordinates background and operator-requested catalog refreshes.
- `config/channels.ts` owns the station lineup returned by `/api/channels`.

Configuration is environment-driven. `CLIPS_DIR` and `CLIPS_URL_PREFIX` describe the
media tree; `TAGGER_DATA_DIR` holds the database and manifest; `DATABASE_PATH` may
override the database file. `BACKUP_DIR` and `NODE_ENV` control backups and runtime mode.

## Security model

Protect operator pages and the editing API with reverse-proxy authentication and HTTPS.
The Node app relies on the proxy for authentication. Store database files, credentials,
and environment files outside the public web root.
See the [deployment guide](../deploy/README.md) for the available setup tools.

## Testing

Vitest keeps unit tests beside their source files. Cross-module server suites live in
`server/test` and exercise `createApp()`; database and indexer suites use temporary directories. CI runs lint,
tests, type checks, and the production build.
